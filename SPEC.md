# SPEC.md — спецификация «Немигающий Тетрис для УКНЦ BASIC»

## 1. Пользовательская задача

Написать классический Tetris для УКНЦ на встроенном BASIC так, чтобы движение фигур выглядело плавно даже при невысокой скорости BASIC.

Главная особенность — **никакого полного erase/redraw активной фигуры при обычном движении и вращении**.

## 2. Игровое поле

Рекомендуемый логический стакан: **10×20 видимых клеток** плюс 2–4 скрытые строки сверху для spawn/rotation.

Размер клетки выбрать экспериментально с учётом экрана 640×264 и необходимости разместить справа/слева:

- NEXT;
- SCORE;
- LEVEL;
- при желании LINES.

Клетка рисуется заполненным прямоугольником (`LINE ... BF`) с небольшим внутренним оформлением только если оно не делает игру слишком медленной. Первая версия может использовать однотонные блоки.

## 3. Матрицы

### 3.1. BOARD

`BOARD(X,Y)`:

- 0 — пусто;
- >0 — закреплённый блок/цвет/тип.

Активная фигура в BOARD до lock не записывается.

### 3.2. ACTIVE OLD / ACTIVE NEW

Для дифференциального рендера достаточно локального окна 4×4 или небольшого общего буфера.

Концептуально:

```
OLD(x,y)
NEW(x,y)
```

После логического move/rotate строится NEW и сравнивается с OLD.

Правила:

| OLD | NEW | действие |
|---:|---:|---|
| 0 | 0 | ничего |
| 0 | 1 | DRAW CELL |
| 1 | 0 | ERASE CELL |
| 1 | 1 | ничего |

Важно: если локальные координаты/рамки OLD и NEW различаются, сравнение должно происходить в **координатах стакана**, иначе движение на одну клетку будет ошибочно выглядеть как полная замена массива.

Практичная реализация в BASIC: общий небольшой diff-buffer над bounding box объединения old/new либо сравнение четырёх old cells с четырьмя new cells без большого массива. Однако требование проекта — логически использовать матрицу/двумерное представление; оптимизировать её можно только сохранив эквивалентное поведение.

## 4. Фигуры и rotation tables

Семь стандартных tetromino.

Для каждой фигуры хранить набор ориентаций как DATA.

Предпочтительный формат данных:

```
piece, orientation, x1,y1, x2,y2, x3,y3, x4,y4
```

или 4×4 bit/matrix representation, если он проще/быстрее именно на УКНЦ BASIC.

Выбор формата подтвердить маленьким benchmark в эмуляторе.

### 4.1. Balanced rotation

Rotation table содержит не только форму, но и **базовый offset перехода**.

Для T требуется подобрать переходы так, чтобы при свободном повороте вокруг центра максимальное число клеток сохранялось на месте. Для типичного T это позволяет получить переход, где остаются 3 клетки и меняются только 2 экранные клетки: 1 erase + 1 draw.

Для остальных фигур — максимизировать overlap, не жертвуя естественным положением фигуры.

O не вращается визуально.

## 5. Move transaction

Любое действие active piece выполняется транзакционно:

```
1. сохранить old state
2. вычислить candidate state
3. collision(candidate)?
   YES -> reject
   NO  -> commit logical state
4. render diff(old,candidate)
5. update timing/lock state
```

Нельзя сначала рисовать candidate, а потом проверять collision.

## 6. Collision

Кандидат запрещён, если хотя бы одна его клетка:

- X < 0;
- X >= WIDTH;
- Y >= HEIGHT;
- попадает в occupied BOARD;

Y < 0 допустим для скрытой spawn-зоны в пределах выбранной модели.

## 7. Rotation kick system

Не копировать SRS целиком: для BASIC это избыточно.

Для каждого rotation transition использовать короткую фиксированную последовательность попыток, например:

```
(base offset)
0,-1
-1,0
+1,0
0,-2     ; прежде всего для I / floor
-2,0     ; при необходимости для I
+2,0
```

Но реальные таблицы должны быть подобраны по результатам тестов, а не бездумно взяты из этого примера.

Особое требование: горизонтальная I на ровном полу должна успешно повернуться в вертикальную посредством upward kick.

При обратном повороте базовая геометрия должна стараться вернуть I вниз к полу. После успешного вращения можно выполнить ограниченный `settle-down`: сдвинуть фигуру вниз на минимальное число клеток, которое компенсирует только искусственный подъём предыдущего kick, если это не создаёт collision. Нельзя превращать его в free downward drop.

### 7.1. Rotation climbing option

Настройка:

```
ALLOW_ROTATION_CLIMB = 0   (default)
```

Если 0, последовательные повороты не должны позволять бесконечно поднимать фигуру вверх без реальной геометрической необходимости.

Если 1, разрешено оставлять любой успешный upward kick без компенсирующего settle-down — экспериментальный режим.

## 8. Gravity, input и lock delay

### 8.1. Основной цикл

Цикл максимально короткий:

```
READ KEY
PROCESS KEY IF ANY
UPDATE TIMERS
IF GRAVITY DUE THEN TRY DOWN
IF LOCK DUE THEN LOCK
GOTO LOOP
```

`INKEY¤` неблокирующий, поэтому подходит для такого цикла.

### 8.2. Gravity timer

Из-за ограничений BASIC время можно представлять loop ticks.

При старте определить константы задержек экспериментально на UKNCBTL при 100% скорости.

У действия игрока есть эффект на gravity deadline. Чтобы управление было отзывчивым на высоких уровнях:

- успешный Left/Right/Rotate postpones gravity;
- не обязательно возвращать timer на 100%; рекомендуется вариант `max(current_remaining, ACTION_GRACE)`;
- таким образом частые действия не позволяют совсем отключить gravity, но дают игроку короткое гарантированное окно.

Рекомендуемая политика:

```
remaining = MAX(remaining, ACTION_GRACE[level])
```

а не безусловное

```
remaining = FULL_GRAVITY_INTERVAL[level]
```

На ранних уровнях разница почти незаметна; на поздних игрок получает шанс дотащить и повернуть фигуру, но не может удерживать её бесконечно.

Константы ACTION_GRACE подобрать playtest'ом.

### 8.3. Grounded / lock delay

Если downward move невозможен:

```
GROUNDED = 1
```

Фигура фиксируется не сразу.

Успешный move/rotation во время grounded:

- если после него фигура больше не касается поверхности — `GROUNDED=0`;
- если остаётся grounded — lock deadline продлевается;
- число полных продлений ограничивает `LOCK_RESETS`.

Рекомендуемый стартовый лимит: 12.

На максимальной скорости минимальный lock window должен всё равно позволять хорошему игроку выполнить примерно 2–4 нажатия.

## 9. Hard drop

Space:

1. найти максимальное возможное перемещение вниз;
2. переместить фигуру сразу в конечную позицию;
3. выполнить differential rendering между исходным и конечным состоянием;
4. начислить drop score;
5. установить grounded/lock-delay;
6. **не lock immediately**.

После hard drop игрок может до lock deadline сделать move/rotation.

Если после этого фигура с помощью kick/move оказывается выше или получает новый путь вниз, игра продолжает normal gravity.

## 10. NEXT и randomizer

Держать две сущности:

```
CURTYPE
NEXTTYPE
```

При spawn:

```
CURTYPE=NEXTTYPE
NEXTTYPE=RANDOM_PIECE
```

NEXT preview обновляется только после генерации нового NEXT.

### Randomizer v1

Для ретро-характера предлагается simple random + защита от грубых повторов:

- `candidate = INT(RND*7)`;
- если candidate совпал с предыдущей фигурой 3-й раз подряд, сделать один reroll;
- принять результат reroll даже если он снова совпал.

Это сохраняет случайность старых игр, но уменьшает совсем неприятные серии. Реализацию можно упростить после проверки поведения RND.

## 11. Scoring

Цель — понятный ретро-баланс, при котором линии важнее простого drop, а четыре строки дают заметную премию.

### 11.1. Drop points

За клетки, реально пройденные вниз действием игрока:

- Soft drop: **1 × (level+1)** за клетку;
- Hard drop: **2 × (level+1)** за клетку.

Автоматическая gravity очков не даёт.

Это удовлетворяет требованию: чем с большей высоты игрок сознательно сбрасывает фигуру, тем больше очков.

### 11.2. Line clear points

База:

| одновременно строк | base points |
|---:|---:|
| 1 | 100 |
| 2 | 300 |
| 3 | 600 |
| 4 | 1000 |

Итог:

```
LINE_SCORE = BASE × (LEVEL+1)
```

Это специально чуть более «ровная» шкала, чем официальный современный Tetris: quadruple остаётся очень выгодным, но triple также имеет смысл в более хаотичной ретро-игре.

Опционально после playtest:

- consecutive 4-line clear bonus;
- perfect clear bonus.

В v1 не требуется.

## 12. Levels

Базовая схема:

- level растёт каждые 10 очищенных строк;
- level 0..9 или 0..15 — выбрать после замера реальной скорости BASIC;
- gravity interval уменьшается нелинейно;
- последние уровни не должны становиться физически неуправляемыми из-за скорости BASIC/input polling.

Таблица delays должна быть `DATA`, а не сложной формулой в горячем цикле.

## 13. Line clear

После lock:

1. найти заполненные строки;
2. начислить score одним событием по числу строк;
3. сдвинуть BOARD сверху вниз;
4. обновить только необходимую область экрана;
5. spawn next piece.

Не делать `CLS`.

Если полная локальная перерисовка стакана после line clear заметно мигает, реализовать row-by-row copy/diff.

Анимация мигания заполненной строки в v1 не нужна: она противоречит основной эстетике «немигающего» режима и отнимает время.

## 14. UI

Минимальный HUD:

```
+----------+   NEXT
|          |   [piece]
|          |
|          |   SCORE
|          |   001234
|          |
|          |   LEVEL
|          |   03
|          |
+----------+
```

Поскольку `PRINT` относится к символьному экрану, а графика — к графическому, способ отрисовки HUD в том же экране необходимо проверить. Предпочтение — полностью графический UI, если постоянное переключение `SCREEN` неудобно или разрушает картинку.

Не предполагать смешанный text+graphics режим, если спецификация УКНЦ его не гарантирует.

## 15. Game over / restart

Game over возникает, если новая фигура не может быть размещена в spawn position.

Показать итог score и предложить restart/quit без необходимости перезапускать BASIC-систему.

## 16. Настройки

В начале программы выделить небольшой блок констант:

```
ALLOW_ROTATION_CLIMB
MAX_LOCK_RESETS
START_LEVEL
CELL_SIZE
... timing constants ...
```

BASIC не обязан иметь настоящие constants; это могут быть хорошо обозначенные переменные, инициализируемые один раз.

## 17. Нефункциональные критерии

- gameplay не зависит от чрезмерно высокой скорости эмулятора;
- на штатной скорости UKNCBTL управление остаётся отзывчивым;
- код можно загрузить/сохранить стандартными средствами BASIC;
- исходник читабелен человеком;
- все ограничения/хаки целевого BASIC объяснены комментариями;
- одинаковое состояние игры должно выглядеть одинаково в Web/Linux/Windows UKNCBTL.
