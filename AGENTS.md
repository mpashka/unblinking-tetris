# AGENTS.md — УКНЦ BASIC Tetris

## 1. Цель проекта

Нужно реализовать полноценную игру «Тетрис» на штатном БЕЙСИКе микро-ЭВМ **Электроника МС 0511 (УКНЦ)**.

Главная техническая особенность проекта — **немигающая отрисовка**. БЕЙСИК УКНЦ достаточно медленный, поэтому нельзя при каждом движении/повороте стирать фигуру целиком и рисовать её заново. Экран должен изменяться минимально: рисуются только появившиеся клетки, стираются только исчезнувшие.

По ощущениям и общему gameplay ориентироваться на классический «Тетрис» для БК-0010/БК-0010-01, но не копировать вслепую неизвестные детали. Если поведение БК-версии удалось подтвердить по исходникам, видео, эмулятору или документации — использовать как референс; если нет — явно фиксировать принятое решение в документации проекта.

Проект также должен поставляться в форме, которую можно проверить без реального УКНЦ:

1. в браузерном эмуляторе УКНЦ;
2. в нативном эмуляторе под Linux;
3. в нативном эмуляторе под Windows.

## 2. Целевая среда

Язык: штатный **БЕЙСИК УКНЦ**, версия языка, документированная как 1985.11.01.

Авторитетный справочник языка:
- «БЕЙСИК. Описание языка. У1.00031-01 35 01»;
- https://emuverse.ru/wiki/УКНЦ_Бейсик_Описание_языка

Полезные подтверждённые возможности языка:

- `DIM` — массивы;
- `INKEY¤` — неблокирующее чтение клавиатуры; возвращает `""`, если клавиши нет, после чтения буфер очищается;
- `SCREEN` — выбор графического/символьного режима;
- `PSET`, `PRESET`, `LINE ... BF` — графика;
- графические координаты: X=0..639, Y=0..263;
- `RND` — генерация случайных значений;
- `BEEP` — звук;
- `PEEK`, `POKE`, `INP`, `OUT` допустимы, но применять их только при доказанной необходимости.

В документации символ строкового типа отображается как `¤`. При подготовке исходника необходимо проверить, какой символ реально принимает конкретная BASIC-система/образ. Не заменять его механически на `$`, пока это не проверено в эмуляторе.

## 4. Принципы реализации

### 4.1. Сначала корректность на настоящем BASIC

Нельзя писать «примерно BASIC» или ориентироваться на GW-BASIC/QBasic/MSX BASIC без проверки. Любая конструкция должна быть разрешена официальной спецификацией BASIC УКНЦ либо экспериментально подтверждена в целевом эмуляторе.

Не использовать современные языковые возможности: структуры, булевы типы, битовые массивы, пользовательские процедуры в современном смысле и т. п.

### 4.2. Экономить вычисления и графические операции

УКНЦ BASIC медленный. В горячем игровом цикле:

- не очищать экран;
- не перерисовывать стакан;
- не перерисовывать неподвижные клетки;
- не выполнять лишние `LINE`, `PSET`, `PRESET`;
- не строить строки и не форматировать текст без необходимости;
- по возможности использовать целочисленные переменные `%`;
- избегать больших циклов по всему стакану на каждом кадре.

Оптимизировать только после появления работающей корректной версии, но архитектура изначально должна позволять differential rendering.

### 4.3. Модель данных отделена от экрана

Экран никогда не является источником истины.

Должны существовать как минимум:

- `BOARD(x,y)` — зафиксированные клетки стакана;
- описание текущей фигуры;
- описание предыдущего визуального состояния текущей фигуры;
- временная «матрица»/буфер для вычисления разницы старого и нового состояния.

Функцию `POINT()` для чтения содержимого экрана в игровой логике не использовать: collision detection выполняется по массивам.

### 4.4. Differential rendering — обязательное требование

При движении или повороте текущей фигуры:

1. построить старое множество занятых клеток active piece;
2. построить новое множество;
3. сравнить их;
4. клетка `old=1,new=0` — стереть;
5. клетка `old=0,new=1` — нарисовать;
6. `old=1,new=1` — экран не трогать;
7. `old=0,new=0` — экран не трогать.

Нельзя реализовывать движение как:

```
ERASE_OLD_PIECE
DRAW_NEW_PIECE
```

даже если визуально это кажется приемлемым в быстром эмуляторе.

При удалении заполненных строк допустима локальная перерисовка изменившейся области стакана, но желательно также минимизировать её. Это редкое событие, поэтому здесь приоритет — корректность и отсутствие неприятного визуального эффекта, а не абсолютный минимум операций.

## 5. Геометрия фигур

Используются семь тетромино: I, O, T, S, Z, J, L.

Все ориентации фигур должны быть **явно заданы таблицами**, а не вычисляться общей формулой вращения во время игры.

Причины:

1. меньше вычислений в BASIC;
2. легко контролировать положение каждой ориентации;
3. можно реализовать «сбалансированный» поворот;
4. проще реализовать floor kick / wall kick;
5. результат детерминирован и легко тестируется.

### Сбалансированный поворот

Цель — при повороте визуально менять как можно меньше клеток.

Например, для T:

```
111
 1
```

переход к вертикальной ориентации следует разместить так, чтобы три клетки по возможности остались на тех же местах: одна новая появляется, одна старая исчезает.

Это не значит, что для каждой фигуры физически возможно ровно `1 erase + 1 draw`. Например для I при переходе горизонталь ↔ вертикаль пересечение неизбежно меньше. Общий критерий:

> среди допустимых вариантов позиционирования новой ориентации выбрать заранее заданный вариант с максимальным числом совпадающих клеток и естественным поведением фигуры.

Таблицы поворотов и offsets считать частью gameplay и не менять случайно при рефакторинге.

## 6. Collision, wall kick и floor kick

Поворот должен быть удобным около стен и особенно около пола.

Базовый алгоритм `TRY_ROTATE`:

1. взять следующую orientation;
2. попробовать штатный offset этой пары ориентаций;
3. если есть конфликт — перебрать небольшую фиксированную таблицу kick-offsets;
4. разрешить сдвиг вверх при столкновении с полом/нижними блоками;
5. выбрать первый допустимый вариант по заранее установленному приоритету;
6. если допустимого варианта нет — оставить фигуру без изменений.

Для I должна работать ситуация:

- горизонтальная I лежит на ровном полу;
- игрок нажимает поворот;
- I становится вертикальной и автоматически поднимается настолько, чтобы нижняя клетка осталась вплотную к полу;
- следующий поворот в горизонталь должен вернуть фигуру к естественному положению у пола, а не оставлять её искусственно поднятой.

По умолчанию запрещено использовать чередование поворотов для бесконечного «взбирания» вверх. Для экспериментов предусмотреть настройку, разрешающую более свободный rotation climbing.

Не требуется точно копировать современный Tetris Guideline/SRS. Нужна предсказуемая, приятная механика, близкая по духу старому тетрису и требованиям выше.

## 7. Падение и фиксация фигуры

Есть различие между:

- normal gravity tick;
- soft/drop action игрока;
- hard drop (пробел);
- lock/fixation.

### Lock delay

Фигура **не фиксируется мгновенно** при касании пола или после hard drop.

После достижения минимально возможной Y-позиции начинается lock delay. До его окончания игрок может:

- двигать фигуру влево/вправо;
- поворачивать её;
- использовать floor kick.

Успешное действие игрока должно давать время на продолжение манёвра.

Но полный бесконечный reset таймера нежелателен. Рекомендуемая модель:

- успешный move/rotate сбрасывает или существенно продлевает lock delay;
- существует `MAX_LOCK_RESETS` для одной фигуры;
- после исчерпания лимита дальнейшие действия не дают полного нового интервала;
- hard drop перемещает фигуру вниз мгновенно, но **не фиксирует её сразу**;
- следующий gravity/lock deadline фиксирует фигуру, если игрок больше не сделал допустимого действия.

Начальные значения для настройки:

- `MAX_LOCK_RESETS = 12`;
- lock delay ≈ 1 обычного gravity interval на текущем уровне, но не ниже минимального человеческого интервала;
- на самых быстрых уровнях нижняя граница lock delay должна оставлять опытному игроку время хотя бы на несколько осмысленных нажатий.

Поскольку в BASIC УКНЦ может не быть удобного wall-clock timer, точная реализация времени определяется экспериментально. Разрешено строить время на счётчике игрового цикла, откалиброванном в эмуляторе на штатной скорости.

## 8. Управление

Минимально:

- Left — влево;
- Right — вправо;
- Down — ускоренное падение на одну клетку / soft drop;
- Up либо отдельная удобная клавиша — поворот;
- Space — hard drop;
- Pause — если удобно реализовать;
- Quit — завершение игры.

Конкретные коды клавиш определить экспериментом через `INKEY¤` и `ASC()` в УКНЦ/эмуляторе и задокументировать.

Не блокировать игровой цикл ожиданием клавиши.

## 9. Следующая фигура

На экране должна постоянно отображаться следующая фигура (`NEXT`).

После фиксации:

1. `NEXT` становится текущей;
2. генерируется новый `NEXT`;
3. preview обновляется только в этот момент.

Если простой `RND` создаёт неприятные длинные серии одинаковых фигур, допускается маленький anti-repeat алгоритм. Не внедрять современный 7-bag автоматически, если он заметно меняет характер старого gameplay. Выбранный алгоритм документировать.

## 10. Очки и уровни

Система должна поощрять:

- ручное ускорение/сброс;
- удаление нескольких строк одним размещением;
- игру на повышенной скорости.

Предлагаемая базовая модель описана в SPEC.md. Константы вынести в очевидный раздел исходника, чтобы баланс можно было менять без переписывания игровой логики.

## 11. Стиль BASIC-кода

BASIC — ограниченная среда, поэтому код должен быть особенно дисциплинированным.

- Разбить программу на диапазоны номеров строк по подсистемам.
- В начале файла дать карту диапазонов.
- Все `GOSUB` должны вести в документированные подпрограммы.
- Никаких случайных magic numbers в горячей логике, если их можно вынести в константы/комментарии.
- Не использовать самоменяющийся код.
- Не полагаться на неописанные особенности эмулятора.
- Избегать длинных BASIC-строк: они неудобны для ввода/отладки и у языка есть ограничение длины строки.
- Сохранять комментарии о нетривиальной геометрии rotation/kick tables.

Рекомендуемая карта строк:

```
10-999       constants, init, main loop
1000-1999    keyboard/input
2000-2999    piece spawn/random/next
3000-3999    movement/collision
4000-4999    rotation/kicks
5000-5999    differential rendering
6000-6999    lock/line clear/score/level
7000-7999    UI/score/preview
8000-8999    drawing primitives
9000-9999    debug/test helpers
10000+       DATA tables
```

Это рекомендация; изменить можно, но структура должна остаться понятной.

## 12. Тестирование

Проверять не только итоговую картинку, но и число графических изменений.

Обязательные сценарии:

- Left/Right в пустом стакане;
- падение на одну клетку;
- каждый переход orientation→orientation для всех 7 фигур;
- T balanced rotation;
- I horizontal→vertical на полу;
- I vertical→horizontal после floor kick;
- повороты у обеих стен;
- невозможный поворот среди блоков;
- hard drop + последующий move;
- hard drop + последующий rotate;
- отсутствие бесконечного lock-delay reset;
- single/double/triple/tetris line clear;
- обновление NEXT;
- game over;
- рост скорости по level;
- отсутствие полного erase/redraw фигуры при обычном move/rotate.

Для differential renderer полезен debug-счётчик `DRAW_COUNT`/`ERASE_COUNT` либо временное логирование состояния матриц.

## 13. Definition of Done

Работа считается законченной, когда:

1. исходник загружается в штатный BASIC УКНЦ;
2. игра запускается без syntax/runtime errors;
3. стакан, все 7 фигур, NEXT, score и level работают;
4. обычные движения и повороты используют differential rendering;
5. визуального мерцания от полного стирания/перерисовки фигуры нет;
6. работают lock delay и манёвры после hard drop;
7. работает floor kick I-фигуры;
8. удаление 1–4 строк и начисление очков корректны;
9. gameplay остаётся управляемым на максимальном уровне;
10. имеется воспроизводимая инструкция запуска в browser UKNCBTL;
11. имеется воспроизводимая инструкция запуска в native UKNCBTL/UKNCBTL-Qt на Linux;
12. имеется воспроизводимая инструкция запуска на Windows;
13. в репозитории есть готовый образ/состояние/диск либо автоматизированный способ собрать артефакт, который можно сразу загрузить в эмулятор.
